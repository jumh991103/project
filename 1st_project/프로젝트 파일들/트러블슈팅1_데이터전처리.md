## 1단계 — 블랙리스트(제외) 방식 시도 → 폐기

`dataprocessed.ipynb`에 남아있는 팀 메모(마크다운 셀, 코드는 이미 덮어써짐):

> "처음에는 패밀리카 **제외**하는 방식을 써서 했지만 **데이터 질이 쓰레기**라 다른 방법"

세단·상용차 등을 키워드로 걸러내 패밀리카만 남기는 **제외(블랙리스트) 방식**을 먼저 시도했으나
정확도가 낮아 폐기. (실제 코드는 git 히스토리에 남아있지 않아 정확한 실패 원인은 추정만 가능 — 팀원에게 재확인 권장)

## 2단계 — 화이트리스트 방식 재설계 (`33ad2ab`, "제조사 통일 및 패밀리카 전처리 완료")

접근을 뒤집음: **① 제조사 11개를 화이트리스트로 먼저 좁히고 → ② 그 안에서 SUV/MPV 키워드로 매칭.**

### 문제 발견: 제조사명 표기가 342종
- `normalize_key()`: NFKC 정규화 + 한글/영문/숫자 외 문자 전부 제거
- `MANUFACTURER_ALIASES` 딕셔너리로 표준 제조사명 매핑
  (예: "비엠더블유"/"BMW" → `BMW`, "현대자동차(주)" → `현대자동차`)
- 원인: **신고 데이터와 리콜 데이터가 같은 회사를 완전히 다른 표기로 기록**하고 있었음
  (신고: "메르세데스-벤츠" / 리콜: "벤츠" 등)

### 패밀리카 판별
- 원본 데이터에 "차량 분류(SUV/세단 등)" 필드가 없어서, 차명(model_name)에
  SUV/MPV로 알려진 키워드가 포함되는지로만 판별 (`MPV_PATTERNS`, `SUV_PATTERNS`)

결과: 신고 15,737행 / 리콜 **811행**

## 3단계 — 1차 버그 수정 (`f6a78ae`, "패밀리카 전처리 데이터 수정")

2단계 결과를 검수하다 두 가지 누락을 발견.

1. **"벤츠"(단독 표기)가 별칭 목록에 없었음**
   → 리콜 원본에서 "벤츠"가 2,559건으로 최다 제조사인데도, 별칭 매핑에 안 걸려서
   해당 리콜 레코드가 대량으로 탈락하고 있었음
2. **SUV 키워드가 좁아서 실제 패밀리카 모델을 놓침**
   → 벤츠 GLA/GLB/GLC/GLK, EQA/EQB/EQC, ML250~350 / 르노 QM3·QM5·QM6·XM3·Arkana·Koleos·Captur /
   재규어랜드로버 Discovery·Defender·E-PACE·F-PACE·I-PACE·Evoque·Freelander 등이 누락돼 있었음

수정 후: 신고 15,737 → **18,492행**(+2,755), 리콜 811 → **1,516행**(+705, 약 2배 증가)

---

## 4단계 — 규칙 기반 노이즈 정리 (`2aa3002`, `scripts/cleanup_family_data.py` 신설)

DB 적재 직전, 3가지 규칙으로 한 번 더 정리.

1. **특수목적차량 표기 제외**: 어린이/통학/구급/앰뷸런스/캠핑카/리무진/휠체어 등
   (SUV·MPV 키워드가 이런 특수목적 차량 이름에도 우연히 매칭되어 끼어든 것으로 추정)
2. **"구형" 표기 차종 제외**
3. **소비자 신고에 유효한 `model_year`가 단 한 건도 없는 제조사·차종 조합은 리콜에서도 제외**
   → 리콜이 1,516 → **255행**으로 급감한 핵심 원인.
   조회 화면에서 신고 이력을 함께 보여줄 수 없는(=신고 데이터가 아예 없는) 오래되거나
   희귀한 리콜 대상 모델을 걸러냄
4. **벤츠 트림 대표화**: GLA/GLB/GLC/GLK/EQA... 계열별로 트림 표기가 너무 세분화돼 있어
   신고 건수가 가장 많은 대표 트림 1개(신고 5건 이상인 경우만)만 남기고 나머지 제외

결과: 신고 18,492 → 17,665행, 리콜 1,516 → **255행**

DB 적재 후(`build_database.py`) 최종 값은 신고 17,512행 — 소폭 추가 감소는
`build_database.py`의 별칭·모델 매칭 실패분으로 추정되나 정확한 원인은 미확인.

DB가 만들어진 뒤 차종 목록을 사람이 눈으로 검수(엑셀로 뽑아서 표시한 것으로 추정)하고 수동 지정.

## 포트폴리오 작성 시 활용 포인트

- **문제 정의**: 공공데이터 2종이 같은 실체(제조사)를 서로 다른 표기로 기록하고 있어
  단순 문자열 매칭으로는 상당수 레코드가 유실됨을 직접 발견
- **원인 분석**: 제조사별 원본 건수(`value_counts()`)를 매칭 전후로 비교해서
  "벤츠" 표기 누락이 리콜 데이터 손실의 주범임을 정량적으로 확인
- **해결 접근의 전환**: 블랙리스트(제외) 방식의 한계를 인지하고 화이트리스트 방식으로
  아키텍처를 바꾼 의사결정 과정
- **데이터 품질 규칙 설계**: "신고 이력이 없는 리콜 대상은 조회 화면에서 의미가 없다"는
  서비스 관점의 판단을 코드 규칙(`cleanup_family_data.py`)으로 명문화한 것
- **재현 가능한 파이프라인**: 정리 스크립트를 `--apply` 플래그로 미리보기/적용 분리 설계
