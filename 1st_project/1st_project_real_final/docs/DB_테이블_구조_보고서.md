# 중고차 리콜체크 데이터베이스 구조 보고서

## 1. 보고서 목적

이 문서는 `project_t4_V2`에서 사용하는 SQLite 데이터베이스 구조를 쉽게 설명하기 위한 자료다.

이 프로젝트는 패밀리카 중고차를 구매하려는 사용자가 제조사와 차종을 선택한 뒤 다음 정보를 확인할 수 있도록 만든다.

- 소비자가 접수한 결함 신고 건수
- 제작사가 진행한 공식 리콜 기록
- 리콜 대상 생산기간
- 리콜 개시일
- 리콜 대상 대수
- 리콜 사유

소비자 결함 신고와 공식 리콜은 의미가 다르므로 서로 다른 테이블에 저장한다.

---

## 2. 사용 데이터

현재 사용한 전처리 CSV는 다음과 같다.

| 파일 | 내용 | 행 수 |
|---|---|---:|
| `자동차제작결함신고정보_11개제조사_패밀리카.csv` | 소유자 결함 신고 | 18,492행 |
| `차종별리콜대수_11개제조사_패밀리카.csv` | 공식 리콜 정보 | 1,516행 |

두 파일 모두 11개 제조사와 패밀리카 범위로 정리되어 있다.

## 3. 전체 엔티티 관계

```text
┌─────────────────┐
│  manufacturers   │  제조사
└────────┬────────┘
         │ 1 : 여러 개
         ▼
┌─────────────────┐
│  vehicle_models  │  대표 차종
└────────┬────────┘
         │ 1 : 여러 개
         ▼
┌──────────────────┐
│ vehicle_variants │  원본 세부 차명
└───────┬──────────┘
        │
        ├──────────────► defect_reports  소비자 결함 신고
        │
        └──────────────► recalls         공식 리콜
```

### 관계를 쉽게 말하면

```text
BMW라는 제조사
  └─ GLA라는 대표 차종
       └─ GLA45 AMG 4Matic이라는 원본 세부 차명
            ├─ 소비자 신고 기록
            └─ 공식 리콜 기록
```

FAQ는 차량 데이터와 직접 연결되지 않는 별도 안내 테이블이다.

## 4. 테이블별 역할

### 4.1 `manufacturers` - 제조사

화면의 첫 번째 선택 상자에 표시할 제조사를 저장한다.

| 컬럼 | 의미 |
|---|---|
| `manufacturer_id` | 제조사 내부 번호(PK) |
| `manufacturer_name` | 화면에 표시할 제조사 이름 |
| `manufacturer_key` | 중복 확인용 비교 키 |

예를 들어 같은 제조사 이름이 여러 방식으로 들어오지 않도록 전처리한 이름을 저장한다.

---

### 4.2 `vehicle_models` - 대표 차종

제조사 선택 후 화면에 보여줄 대표 차종을 저장한다.

| 컬럼 | 의미 |
|---|---|
| `model_id` | 대표 차종 내부 번호(PK) |
| `manufacturer_id` | 어느 제조사의 차종인지 연결하는 번호(FK) |
| `model_name` | 대표 차종 이름 |
| `model_key` | 공백·하이픈을 줄인 비교용 이름 |
| `vehicle_type` | SUV, MPV/미니밴 등 차량 분류 |

`manufacturer_id`가 같은 제조사 안에서 여러 차종을 구분해준다.

---

### 4.3 `vehicle_variants` - 원본 세부 차명

하나의 대표 차종에 포함된 실제 원본 차명을 저장한다.

예:

```text
대표 차종: 카니발
세부 차명: 카니발 YP
세부 차명: 카니발 KA4
```

| 컬럼 | 의미 |
|---|---|
| `variant_id` | 세부 차명 내부 번호(PK) |
| `model_id` | 어느 대표 차종인지 연결하는 번호(FK) |
| `variant_name` | CSV에 있던 원본 차명 |
| `variant_key` | 비교용 차명 키 |

---

### 4.4 `defect_reports` - 소비자 결함 신고

차량 소유자가 자동차 결함이나 이상 현상을 접수한 기록이다.

| 컬럼 | 의미 |
|---|---|
| `report_id` | 신고 기록 번호(PK) |
| `model_id` | 대표 차종 연결 번호 |
| `variant_id` | 세부 차명 연결 번호 |
| `raw_model_name` | 원본 차명 |
| `received_date` | 신고 접수일 |
| `model_year` | 신고 데이터의 모델연도 |
| `vehicle_type` | 차량 분류 |
| `source_file` | 사용한 원본 파일 이름 |

신고 건수가 많다는 사실만으로 결함이 확정되거나 리콜된다는 뜻은 아니다. 이 데이터는 소비자가 신고한 참고 정보다.

중복 신고 행도 원본 데이터의 일부이므로 임의로 제거하지 않는다.

---

### 4.5 `recalls` - 공식 리콜

제작사가 공식적으로 진행한 리콜 기록이다.

| 컬럼 | 의미 |
|---|---|
| `recall_id` | 리콜 기록 번호(PK) |
| `model_id` | 대표 차종 연결 번호 |
| `variant_id` | 세부 차명 연결 번호 |
| `raw_model_name` | 리콜 데이터의 원본 차명 |
| `production_start_date` | 리콜 대상 생산 시작일 |
| `production_end_date` | 리콜 대상 생산 종료일 |
| `recall_start_date` | 리콜 개시일 |
| `affected_count` | 해당 리콜 기록의 대상 대수 |
| `recall_reason` | 리콜 사유 |
| `vehicle_type` | 차량 분류 |
| `source_file` | 사용한 원본 파일 이름 |

`affected_count`는 리콜 기록별 대상 대수다. 여러 리콜 기록의 대수를 합하면 같은 차량이 여러 번 포함될 수 있으므로 고유 차량 수로 해석하지 않는다.

---

### 4.6 `faq_items` - FAQ

서비스 사용자가 자주 묻는 질문과 답변을 저장한다.

| 컬럼 | 의미 |
|---|---|
| `faq_id` | FAQ 번호(PK) |
| `category` | FAQ 분류 |
| `question` | 질문 |
| `answer` | 답변 |
| `sort_order` | 화면 표시 순서 |
| `is_active` | 화면 표시 여부 |
| `source_url` | 참고 출처 |

FAQ는 차량 테이블과 직접 연결하지 않고 별도로 조회한다.

---

### 4.7 `data_coverage` - 데이터 범위

데이터의 시작일, 종료일, 행 수를 기록한다.

화면에서 다음과 같은 안내를 만들 때 사용한다.

```text
소비자 결함 신고: 2019년 ~ 2025년
공식 리콜: 데이터에 저장된 리콜 개시일 기준
```

## 5. 주요 SQL 용어

| 용어 | 쉬운 뜻 |
|---|---|
| `PRIMARY KEY` | 각 행을 구분하는 고유 번호 |
| `FOREIGN KEY` | 다른 테이블과 연결하는 번호 |
| `UNIQUE` | 같은 값의 중복 저장 방지 |
| `JOIN` | 여러 테이블을 연결해서 조회 |
| `LEFT JOIN` | 연결 데이터가 없어도 기준 테이블 행은 표시 |
| `COUNT(*)` | 행 개수 계산 |
| `SUM()` | 숫자 합계 계산 |
| `MAX()` | 가장 큰 값 또는 가장 최근 날짜 확인 |
| `COALESCE()` | 값이 없을 때 기본값으로 표시 |
| `WITH` | 복잡한 조회를 단계별 임시 결과로 나누기 |
| `VIEW` | 자주 사용할 조회 결과를 저장한 가상 테이블 |

## 6. `model_overview` VIEW의 역할

신고 테이블과 리콜 테이블을 바로 JOIN하면 행 수가 부풀 수 있다.

예를 들어 한 차종에 신고 10건과 리콜 5건이 있으면, 잘못 JOIN할 경우 10 × 5 = 50행처럼 계산될 수 있다.

그래서 다음 순서로 처리한다.

```text
신고 테이블 → 차종별 신고 건수 집계
리콜 테이블 → 차종별 리콜 기록 수·대수 집계
두 집계 결과 → model_id 기준으로 연결
```

`model_overview`에는 다음 값이 들어간다.

- `complaint_count`: 소비자 신고 행 수
- `recall_record_count`: 공식 리콜 기록 수
- `affected_count_sum`: 리콜 대상 대수 합계
- `latest_report_date`: 가장 최근 신고일
- `latest_recall_date`: 가장 최근 리콜 개시일

## 7. SQL 파일별 역할

### `schema.sql`

데이터베이스의 구조를 만든다.

```text
테이블 생성
인덱스 생성
model_overview VIEW 생성
```

### `load_data.sql`

전처리 CSV를 SQLite에 넣는다.

```text
CSV import
→ 제조사 저장
→ 대표 차종 저장
→ 세부 차명 저장
→ 신고·리콜 저장
```

### `queries.sql`

Streamlit 화면에서 사용할 조회문을 모아둔다.

```text
제조사 선택
→ 차종 선택
→ 모델연도 선택
→ 신고·리콜 결과 표시
```

### `verify.sql`

데이터가 빠지거나 잘못 연결되지 않았는지 확인한다.

```text
행 수 확인
제조사 수 확인
차종 수 확인
연결 누락 확인
데이터 기간 확인
```

## 8. 전체 실행 흐름

```text
전처리 CSV
    ↓
load_data.sql의 stage 테이블
    ↓
schema.sql의 정식 테이블
    ↓
model_overview VIEW
    ↓
queries.sql 조회
    ↓
Streamlit 화면
```

실행 순서는 다음과 같다.

1. `schema.sql`로 테이블을 만든다.
2. `load_data.sql`로 CSV를 가져온다.
3. `verify.sql`로 행 수와 제조사 수를 확인한다.
4. `queries.sql`의 조회문을 테스트한다.
5. Python의 `build_database.py`로 위 과정을 자동화한다.
6. Streamlit에서 SQLite DB를 조회한다.

## 9. 데이터 해석 시 주의할 점

### 소비자 신고

소비자가 접수한 참고 정보다. 신고 건수가 많다고 해서 공식 결함 인정이나 리콜 확정을 의미하지 않는다.

### 공식 리콜

제작사가 진행한 공식 조치 기록이다. 해당 차량의 리콜 조치가 실제로 완료됐는지는 차대번호 조회가 필요하다.

### 모델연도와 생산기간

신고 데이터의 `model_year`와 리콜 데이터의 생산기간은 기준이 다르다.

따라서 다음처럼 직접 연결하지 않는다.

```text
모델연도 2020 = 생산종료일 2020
```

대신 같은 `model_id`를 기준으로 신고와 리콜을 각각 보여준다.
